## 二、根因

两个失败 case 的码形都超出了 v6 的 `dashPattern`：

```
v6: (?:[A-Za-z]-\d{1,6}|[A-Za-z]?\d{1,6})(?:-[A-Za-z]?\d{1,6}){1,3}
```

它只支持「单字母前缀 + 数字段」和「纯数字段」，因此：

- `CC3-3214`：首段 `CC3` 是**两个字母**+数字 → 首段匹配失败 → 整串不匹配；
  TierD 兜底只抓到 `3214`（丢掉 CC）。
- `1023-a-66`：中间段 `a` 是**纯字母** → 整串不匹配；`1023` 又因为后面紧跟 `-` 被排除 → 结果为空。

其余门禁都没问题：特征词（欢猫驿站 / 妈妈驿站）、锚点（取件码 / 取货码）、TierB 引导字均已覆盖。

## 三、规则改动（v6 → v7）

新码形（`rules/rules.json` / `app/assets/rules/rules.json` / `ExtractorRules.DEFAULT_DASH_PATTERN` 三份一致）：

```
一段 = (?:[A-Za-z]{1,2}-\d{1,6}|[A-Za-z]{0,2}\d{1,6})     可带 1-2 字母前缀：CC3 / M-2 / 1023
     | [A-Za-z]{1,2}                                        纯字母段：a
规则 = 一段(-一段){1,3}
     | 一段(-纯字母段)(-一段){1,2}                          纯字母段只能在中间，且后面必须跟数字段
```

关键约束：**纯字母段必须夹在中间且后面跟着数字段**。
否则 `e-mail`、订单号 `A-1023`、行程号 `B-24680` 这类文本会被误当成取件码——
回归用例 036–038 专门锁住这三条。

同时把「码形正则」纳入三副本一致性校验（原来只比 version / minAppVersionCode / 锚点，
改正则漏改 Java 副本不会有人发现，而系统进程只能读 `createDefault()`）。
