# 4.4.9 数据正确性修复

## 系统待办完成

新写入的小米、ColorOS 待办/便签会读取本次 INSERT 的 `last_insert_rowid()`，把后端、库路径、目标表、行 ID 和实际正文保存在应用私有的 `todo_links` 偏好中。荣耀 Provider 路径校验插入返回的 URI/ID，直接 SQL 路径在写入 Instances 之前读取待办行 ID。完成和查询时同时验证 ID 与正文；目标已被编辑或删除时，不再放宽成按码查找。

历史版本和系统进程冻结兜底写入的待办没有这些回执，不能可靠确认归属，升级后不再自动修改它们；App 内仍可正常标记已取，系统待办需手动完成。新写入的所有模板（包括不含取件码的自定义模板）使用目标 ID，不受此限制。只读去重兼容查询仍接受完全等于取件码或以 `取件码 <完整取件码>｜` 开头的标准模板，不再使用 `%取件码%` 子串匹配。

## 本地入库与重复事件

事件哈希查询、待取码查询、历史事件哈希归档以及新记录插入在同一 Room 事务中执行。历史记录保留，数据库表结构不变，无需清空数据或破坏性迁移。

短信入库保留 Hook 提供的原始事件时间，旧短信重放不会因为处理时间改变而变成新事件。待取记录继续按完整取件码合并；已取记录在原接收时间和取件时间中较晚者之后保留固定 24 小时重放窗口。窗口内同内容的 App 刷新不重建本地记录，也不会重写系统待办；重复上报只更新最后见到时间，不延长窗口。

窗口之后出现相同发送方、正文和取件码，旧事件哈希会加上历史记录 ID 归档，新事件可以重新入库。当前通道没有统一、可靠的包裹唯一标识，因此这是时间窗口策略：窗口内同码的新包裹仍可能被合并，窗口后 App 再次加载陈旧待取数据也可能被当成新事件。后续若取得稳定包裹 ID，应优先用包裹 ID 区分。

## root 备用通道

一次性 su 命令直接以参数启动，并发读取 stdout/stderr，保留退出码和超时。查询结果不再混入 `id` 输出。持续排空管道，即使输出超过保留上限也不会因为管道写满而阻塞。超时清理不会同步等待仍被后代进程持有的输出流。

## 验证

`./gradlew :app:testDebugUnitTest :app:assembleRelease` 覆盖已有 UI/流程回归及新增的真实 SQLite/Room、ContentResolver、进程管道测试。`test/HonorSqlTest.java` 和 `tools/honor_sql_check.py` 验证 AOSP、ColorOS、荣耀表结构的 SQL，特别检查回执记录的是待办 ID，而不是后续写入的 Instances ID。所有数据和进程测试使用合成数据，不操作手机上的真实待办。
