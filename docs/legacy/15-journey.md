## 一、项目缘起（v12 之前的探索期）

最初从一个小目标开始："快递取件码总在一堆短信里被淹没，我想要它们自己跑到我眼前。"

- **原型**：Python 脚本 `pickupextract.py`——正则提取取件码（菜鸟/丰巢/京东多规则）
- **第一版形态**：LSPosed 模块 v12（Hook 短信 + 通知监听副通道 + JSON 存储 + 小米便签同步）
- **痛点1**：想自动写入小米笔记，却需要手动输入便签 ID，无法自动定位
- **痛点2**：构建环境只有手机 Termux（无 PC），手工 stub 编译 Xposed API
- **痛点3**：模块在 LSPosed 显示"已激活"，但**所有 Hook 从未被调用**——
  日志刷屏 `AbstractMethodError`，三个 Hook 点从未生效（v13-v16 反复排查）

## 二、问题溯源：一个签名引发的"僵尸模块"（v16 定论）

日志里的报错：
```
java.lang.AbstractMethodError: abstract method
"void ...IXposedHookLoadPackage.handleLoadPackage(
    ...callbacks.XCLoadPackage$LoadPackageParam)"
```
排查结论：**自研 Xposed stub 的 `LoadPackageParam` 放错了类**——
运行时 LSPosed 要求的签名是 `callbacks.XC_LoadPackage$LoadPackageParam`，
而手工 stub 写成 `IXposedHookLoadPackage$LoadPackageParam`，字节码签名不匹配 →
模块加载了、入口永远进不去。**12 个手工构建脚本无一例外全部命中此坑。**

**解法**：放弃手工 stub，改用**官方 `api-82.jar`** 构建——签名天然正确，
`AbstractMethodError` 从根上消失（后续全部版本再无此问题）。

## 三、迁入新平台：从"需求考古"到"架构定稿"

项目携带 6 篇详尽文档（需求/技术方案/问题清单/待办/补充）迁入新协作平台，我们做的是：

1. **全量通读与评估**：确认历史判断中的错误（作用域进程归属、编码三重 fallback 帮倒忙、
   `param.thisThread` 取 Context 的隐性 bug、跨进程存储方案……），写成
   `docs/07-assessment.md` 评估与架构定稿
2. **与你对齐产品方向**：确认"一个取件码 = 一条待办、堆栈置顶、不重复"的核心体验，
   并收到两条真实样例短信——它们直接暴露了两个正则必须覆盖的格式
   （`凭22-2-3579到…`、`取件码为A, B, C` 多码簇）
3. **实机侦察（P0）**：通过 adb 完成全部只读侦察——确认系统为
   HyperOS 4.0 / Android 17（SDK 37），定位关键事实：
   - 待办数据库 `todo.db`（表 `todo`，37 条现有数据）
   - 全部字段语义（含 `custom_sort_id` 排序键，实测每条 +0x100000）
   - 小米笔记 App 的 Provider/URI/数据模型
4. **便签写入"临门一脚"实测**：root 直写 `todo.db` → 打开便签 App → **条目立刻出现在待办顶部**，
   且按系统原生排序规则"新压旧"——写入路线一次验证通过

## 四、P1→P2：捕获链路的硬仗（本轮最有价值的技术攻坚）

首版捕获模块上线后，日志给了我们一连串"看起来正常、实际没动"的谜题，
**每个谜题都靠日志定位并给出方案**：

| 谜题 | 根因（日志实证） | 解法 |
|---|---|---|
| 三个 Hook 点了但短信到达无反应 | HyperOS 4.0 真入口是 `SmsReceiver`（逆向 MiuiMms APK 确认），服务层方法不被调用 | 补 S4-S7 多点 Hook |
| 网络短信全都不触发 | 小米"网络短信"**直接写库**，不走广播接收器 | **抓结果**：Hook 短信库写入点（S8，100% 必经） |
| 捕获成功但模块 App 收不到 | 广播投递给"冻结"进程被静默丢弃 | ContentProvider.call 唤醒（Provider 不受冻结限制） |
| su 执行报 127 | Termux 二进制在 App su 子进程域不可执行 | 拷贝 sqlite3+依赖库到 `/data/local/tmp` + 命令行内 `LD_LIBRARY_PATH` |
| su 后"打不开数据库" | **挂载命名空间**：App 的 Zygisk su 继承了 App 视图 | `su -M`（全局挂载命名空间） |
| 偶发写库失败 | 便签数据目录 mode 700 | 写入前自愈式 chmod（App 属主不变） |

**胜利时刻**（实机日志）：

```
SMS: sender=138****8888 | body=【菜鸟驿站】…取件码为86-4-8888
EVENT dispatched (provider), result=Bundle[…]
TODO OK: 📦 取件码 86-4-8888｜菜鸟驿站｜示例市·示例驿站（地址已脱敏）｜2026-09-03 06:04
```
真实短信 → 待办自动置顶出现，全自动闭环达成。以下示例均来自真实测试，手机号与地址已脱敏。

## 六、设计原则（沉淀）

1. 产品逻辑必须和系统原生行为一致（堆栈排序 = 复刻 App 自家 `custom_sort_id` 算法）
2. 系统组件别猜，**直接逆向**（拉 APK → dex 字符串扫描，一次定位真实类名/URI/SQL）
3. 所有跨进程/授权场景走"最不意外"的官方通道（Provider 唤醒、`su -M` 全局命名空间）
4. 面向用户：零成本自检（一键测试）、可回退（去重/黑名单/模板全部可配置）、数据永远可清
5. 安全：零网络、零短信权限、数据全本地；签名规范建全（keystore 与密码永不入库）
