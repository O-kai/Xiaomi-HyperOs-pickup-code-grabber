# 无 Root 形态（暂称 Lite 版）可行性结论

> 调研日期：2026-10-05 · 设备：小米 13 Ultra / Android 16 / HyperOS 3.0
> 状态：**结论已定，尚未动工**。所有「需实测」项均未验证。

## 一、产品目标（作者定义）

第一性原理只有三条：

1. 收到取件短信 → 识别取件码 → 存进**自己的数据库**
2. **桌面小组件**直接展示待取件码（对标小米自带待办小组件）
3. 用户随时开 App 或翻页查看；点小组件条目即可标记「已取件」

用户明确不要的方向：第三方 todo App（滴答清单等）。允许的辅助能力：设闹钟、写入系统日历。

## 二、四个环节的结论

| 环节 | 结论 | 置信度 |
|---|---|---|
| 桌面小组件 | ✅ **可行且低成本**。小米官方明文「仅适配安卓原生小部件无需通过小米审核」 | 高 |
| 读取快递短信 | ⚠️ **未验证通过**。NLS 路线理论上可行，但本次实测**探针未收到短信通知** | 待实测 |
| 写入系统待办 | ❌ **技术不可行**。`CalendarContract.Tasks` 不是公开 API（公开 SDK 与 AOSP 均无此嵌套类），只能写「日程」而非「待办」 | 高 |
| 提取引擎 | ✅ **100% 可复用**。纯逻辑、零 Android 依赖，现有 162 项测试可直接继承 | 高 |

## 三、架构骨架（已定，落地前不再改）

```
L0 提取引擎          ← 完全复用现有资产，不动
   ↓
L1 读取适配器        ← 可插拔，NLS / 未来其它通道
   ↓
L2 存储层 Room       ← 唯一写入口
   ↓
L3 出口适配器        ← Widget / 通知 / 角标 / 闹钟 / 系统日历 / 剪贴板 / 振动
```

分层铁律：
1. L1 只产出纯数据（`RawMessage`），Android 类型在边界就拆掉
2. L2 是唯一写入口，L3 不得直连 Dao
3. 每层只依赖下一层的接口 → 换读取方式 / 换展示方式均不影响其它层

## 四、桌面小组件（可行性最高的部分）

### 关键决策

| 决策 | 理由 |
|---|---|
| 4×4 规格，**固定 3 行 + 每行独立 PendingIntent** | Android 16 上 `RemoteViews.setRemoteAdapter(Intent)` 已失效（API 35 弃用），老的列表式 widget 会**静默不刷新**。固定行直接绕开这整个雷区 |
| 单进程，不声明 `android:process` | `AppWidgetProvider` 默认就在主进程，无需跨进程共享数据库 |
| `updatePeriodMillis = 0` | 文档明确周期更新不低于 30 分钟且 ROM 更激进；全部靠**事件驱动主动 `updateAppWidget()`** |
| 三个刷新层级（骨架 → 快照 → Room） | widget 进程 adj 高易被回收，避免白屏 |

### 已知坑（必须遵守）

- `PendingIntent` 相等性比较**忽略 extras** → 必须靠 `data` URI 区分记录，否则 3 行会互相覆盖
- 深色模式：`values-night` 依据**系统 uiMode**，不是壁纸深浅 → 用「半透明深色底 + 白字」，两种壁纸下都自然
- 取件码建议 `monospace` 字体，避免连字符错位
- 「标记已取件」用 **文字按钮（✓ / ↩）而非图标**，避免小尺寸下 density 问题
- 点按反馈用**行内状态位 + 振动**双重冗余，不用透明 Activity（会闪烁，违背「原地」目标）
- 取件码进剪贴板需标 `EXTRA_IS_SENSITIVE`（API 33+），不进系统剪贴板预览

### 二期可考虑

- 小米超级岛（HyperOS 3 的灵动岛）：**官方示例 JSON 就是取件场景**，但需邮件申请 + 设计审核
- 角标：`Notification.setNumber()`（MIUI 12+ 标准 API），但需引导用户开「显示桌面图标角标」

## 五、读取方案：这是唯一的风险点

### 候选路径

| 路径 | 可行性 | 用户门槛 | 问题 |
|---|---|---|---|
| **NLS 读短信通知** | 理论可行，**本次实测未收到** | 通知使用权开关 | OTP 脱敏 / 静默通知 / 国产 ROM 策略 |
| NLS 读快递 App 通知 | 可行 | 同上 | 覆盖率低且偏斜 |
| 申请 `READ_SMS` | **反直觉：有害** | 运行时权限 | 小米明文「无需短信权限就能完成目标任务」是驳回理由 |
| 成为默认短信应用 | 可行 | 极高 | 不能「只读不接管」，必须接管短信 App |
| 手动粘贴 / 分享菜单导入 | ✅ 兜底必备 | 低 | 需用户操作 |

### 竞品验证（最有说服力的证据）

`shareven/parcel`（MIT，234 star，已上 F-Droid）是唯一成功的同类产品，其 FAQ 原文：

> 「无法识别的短信…**没有发送者号码的这种网络短信，目前识别不了**」
> 「**不发短信**的话，可以复制取件码或短信，点击 + 号自动粘贴导入。**或者找快递客服，让他把取件码通知方式改成短信通知**」

**一个 234 star 的产品，作者本人在教用户「手动粘贴」和「去改快递的通知方式」。**

### 物理上限（与技术方案无关）

- 淘宝隐私号码 → 丰巢**根本发不出短信**（上观新闻、重庆日报有公开案例）
- 部分快递多通道并列（菜鸟 = 短信 + 支付宝 + App），短信只是其中一条
- 5G 消息 / RCS / 网络短信：非 root 方案基本读不到

### 待实测（决定方案生死）

| # | 项 | 判据 |
|---|---|---|
| **T1** | HyperOS 3 上 NLS 能否收到 `com.android.mms` 通知 | 收到 → 继续；收不到 → 读取层要推翻 |
| **T2** | 收到后正文是否被替换为 `Sensitive notification content hidden` | 未脱敏 → 良好 |
| **T3** | 是否被直接打星号 `*****`（部分国产 ROM） | 打星号 → NLS 无解 |
| **T4** | 「增强通知」开关在 HyperOS 3 的路径 | 找不到 → 用户无法自救 |

## 六、需要修正的三个认知

1. **`CalendarContract.Tasks` 不存在** → 只能写「日程」不是「待办」，UI 文案要改
2. **Android 16 没有日历写入新规** → 「用户主动点确认」是我们自己的设计，不是平台要求（反而更自由）
3. **「写进小米笔记待办」技术上可行**（`POST /todo/v1/user/records`，小米官方网页版在用），但需 WebView 登录 + 非公开接口，作者已决定不做

## 七、建议的执行顺序

```
阶段 0（当前）    跑通 T1~T4，验证读取层
阶段 1            建 L2 存储 + L0 引擎接入，手动插入数据验证小组件展示
阶段 2            接 L1 读取（NLS），跑通端到端
阶段 3            加闹钟 / 日历 / 通知 / 角标
阶段 4            多通道兜底（粘贴导入、截图 OCR）
```

**阶段 0 不通过，后续全部要重新设计 —— 所以先验证，不急着写业务代码。**
