# 取件提醒为什么不准（2026-11-18 定论）

## 结论

**不是被冻结，也不是算错了时间，而是闹钟类型选错了。**

旧实现（`Reminder.schedule`）：

```java
am.setInexactRepeating(AlarmManager.RTC_WAKEUP, nextTriggerAt(ctx),
        AlarmManager.INTERVAL_DAY, pi);
```

`setInexactRepeating` 是**不精确**闹钟：系统会把它塞进「省电窗口」批量唤醒，
Android 文档原话是 *the OS will shift the alarm's delivery to a later time*。
再叠一层 HyperOS 自己的后台管控，偏差从几分钟到几十分钟都出现过 ——
用户看到的「选了 9:00，9:1x 才响」就是这个。

`nextTriggerAt` 本身没问题（`ReminderSchedule` 有离线单测覆盖：
今天该点已过就顺延到明天）。

## 改法

1. `setExactAndAllowWhileIdle(RTC_WAKEUP, 触发点, pi)` —— 一次性精确闹钟；
2. 因为不再 repeating，**响过之后必须自己排下一天**：
   `Reminder.fire()` 的 `finally` 里调 `schedule(ctx)`（查库失败也不能丢明天的闹钟）；
3. Android 12+ 需要 `SCHEDULE_EXACT_ALARM`：manifest 声明 + `canScheduleExactAlarms()`
   判断；没授权就退回 `setAndAllowWhileIdle`（还会晚，但至少会响），
   设置面板里给一行「精确提醒未开启 → 点此允许」，直达系统「闹钟和提醒」页；
4. `LauncherActivity.onResume` 顺带 `Reminder.schedule()`：用户刚从系统页授权回来时，
   把还挂在「不精确」那一支的闹钟重排成精确的（同点重排幂等）。

## 真机验证（K90 Pro Max / HyperOS）

授权后 `dumpsys alarm`：

```
RTC_WAKEUP #120: Alarm{... io.github.okaidev.pickupcode}
  tag=*walarm*:io.github.okaidev.pickupcode.action.REMINDER
  type=RTC_WAKEUP origWhen=2026-11-19 18:30:00.000 window=0
  exactAllowReason=permission repeatInterval=0
```

- `window=0` = 精确（不精确的那种会带一个窗口值）；
- `origWhen` 正好是设定的 18:30:00.000；
- `exactAllowReason=permission` = 走的是精确通道而不是降级通道。

手动触发一次 `ReminderReceiver`：日志
`REMINDER notified pending=3` + `REMINDER scheduled EXACT at 18:30`，
说明「响完排下一天」这条链路是通的。

## 还剩的外部变量（不是代码问题）

- HyperOS 的「省电策略 / 后台运行」如果对这个 App 做了限制，即使精确闹钟也可能被推迟；
  极端情况下需要把本 App 的后台策略设为「无限制」。
- 系统时间/时区被改过之后，下次 fire 会按新时区重算，属预期。
