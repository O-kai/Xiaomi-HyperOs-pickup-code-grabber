## 一、现象

三条真机原文，同一个菜鸟驿站模板：

| # | 短信原文 | v11 提取 | 正确结果 |
|---|---|---|---|
| 1 | 【菜鸟驿站】取件码D-3704的韵达81913包裹到派出所南隔壁快递站，请19:00前取 | `3704`、`81913` | `D-3704` |
| 2 | 【菜鸟驿站】取件码D-3770的韵达39116包裹到派出所南隔壁快递站，请19:00前取 | `3770`、`39116` | `D-3770` |
| 3 | 【菜鸟驿站】取件码C-2605的韵达30453包裹到派出所南隔壁快递站，请19:00前取 | `2605`、`30453` | `C-2605` |

两个错码的性质并不相同：

- `3704` 是**真码自己的尾段**——`D-3704` 被横杠切开后的后半截
- `81913` 是**韵达运单尾号**，与取件码毫无关系

来源（菜鸟驿站）与地点（派出所南隔壁快递站）在 v11 下都是对的，问题只在码。

## 二、归因：锚点层抓对了，是形状校验把它扔了

把引擎逐层打开看（`test/RuleLab` 之外的临时探针）：

```
TierA hit: [D-3704] @9          ← 锚点层其实抓对了整串
validCode("D-3704") = false     ← 形状校验判非法，直接丢弃
CODES = [3704, 81913]           ← 结果集为空 → 退化到 TierD 弱兜底
```

`dashPattern`（v11）：

```
(?:[A-Za-z]{1,2}-\d{1,6}|[A-Za-z]{0,2}\d{1,6})(?:-(?:…)){1,3}   ← 至少两段
```

`D-3704` 拆开是两个字段：`D` 和 `3704`。第一段的形状表只有「字母-数字」和
「数字」两种，**没有纯字母段**；唯一能整串吃下它的 `[A-Za-z]{1,2}-\d{1,6}`
后面又强制要求 `(?:-段){1,3}`（至少再来一段）。于是整串被判非法。

结果集为空 → 落到 TierD：

- `anyToken` 的 lookbehind 是 `(?<![A-Za-z0-9])`（v6.1 为了让「取件码-6-4-3009」
  能抓到横杠后面的码而放宽），横杠不算字母数字，于是从 `-` 后重新起扫
- `3704` 和 `81913` 都是纯数字，`alnumPattern` 全部放行
- 两个 token 在 24 字窗口里都能同时够到「包裹」和「取件」，
  评分各得 4 分（阈值就是 4），双双通过

一句话：**正确的答案在第一步就被扔掉了，兜底层只能用碎片拼一个看起来像的东西。**

## 三、修法（三处，全在规则数据里）

### 3.1 `dashPattern`：允许单段「字母-数字」

```
(?:[A-Za-z]{1,2}-\d{1,6})(?:-(?:…)){0,3}          ← 新增：字母-数字开头，尾段 0~3
| (?:[A-Za-z]{1,2}-\d{1,6}|[A-Za-z]{0,2}\d{1,6})(?:-(?:…)){1,3}
| (?:[A-Za-z]{1,2}-\d{1,6}|[A-Za-z]{0,2}\d{1,6})(?:-[A-Za-z]{1,2})(?:-(?:…)){1,2}
```

关键是**分开写**而不是把原分支的 `{1,3}` 改成 `{0,3}`：

- 「字母-数字」开头 → 允许 0 尾段（`D-3704`、`C-2605`、`M-2`）
- 纯数字开头 → 仍要求至少 1 尾段（`16-4-9626`、`9-9999`）

如果把 `{1,3}` 统一改成 `{0,3}`，`[A-Za-z]{0,2}\d{1,6}` 会连 0 尾段一起合法化，
**裸数字（`6`、`189`、`1064`）立刻变成合法码形**——v4 时代专门修过的坑会重新裂开。

### 3.2 `excludeHeadWords`：补 18 个承运商名

```
韵达 中通 圆通 申通 顺丰 邮政 EMS 极兔 德邦 京东 百世 天天 优速 宅急送 丰网 速尔 全峰 国通
```

语义：品牌名后面紧跟的纯数字是运单尾号（`韵达81913`），不是取件码。

为什么不会误杀正常取件短信：锚点层抓到的码，前文是「取件码／取货码／凭／出示」，
碰不到品牌名；只有兜底层才会遇到「品牌名 + 数字」这种紧邻关系。

### 3.3 `excludeTailPhrases`：补 7 个物流状态词

```
已发货 已发出 已寄出 已揽收 已签收 派送中 运输中
```

对抗测试里发现的独立误抓：`【京东】您的快递JD-889900已发货，请及时领取`
在放开单段码形后会被抓成 `JD-889900`（v11 抓的是 `889900`，同样错）。
码后紧跟「已发货」这类状态词，说明它是运单号而不是取件码。

刻意**没有**加入「已到站」「已到达」——这两个词在真实取件短信里紧跟在取件码后面
（「取件码D-3704已到站，请及时领取」），加进去会大面积误杀。

## 四、取件码部分为什么不改引擎

取件码的三处改动全部落在 `rules/rules.json` + 冒烟用例表，一行提取逻辑都没动。原因是：

1. **热更新能覆盖到已经装机的用户**。引擎改动必须发版，而规则改动走 `UpdateCenter`
   的双镜像拉取，3 天内自动生效，用户什么都不用做。
2. **老引擎能正确解释新规则**。`dashPattern` / `excludeHeadWords` / `excludeTailPhrases`
   都是 4.0.5 起就存在的字段（`minAppVersionCode = 405`），语义没有扩展，
   只是词表和形状放宽。
3. **已经有实测证据**：用 v4.1.0 编译产物里那份**旧冒烟用例**（`SMOKE_TEST_CASES`）
   跑 v12 规则，`runSmokeTest` 返回 `true`。也就是说老 App 拉到新规则不会被
   端侧安全闸拒绝。

所以 `minAppVersionCode` 保持 **405** 不变。

**地点部分是例外**（见第七节）：它必须改引擎，因此只能随下一版 APK 生效。
两条路径互不影响——规则先上，用户立刻拿到正确的取件码；地点等下次升级，
不升级也只是地点显示「店领」，码始终是对的。

## 五、影响面

`dashPattern` 是全局码形，同时喂给四处：

| 使用点 | 影响 |
|---|---|
| `validCode()` | 单段字母码从「非法」变「合法」——本次要的修复 |
| `patternAnyToken`（TierD / 地点策略3） | token 边界变正确：`D-3704` 整串被吃下，不会再有 `3704` 碎片 |
| `patternBy`（TierB「凭/出示」） | `凭A-1234到…取件` 能命中 |
| `patternCodeToTake`（TierC） | 「码…到…取」夹取型覆盖单段码 |

`extractPlace` 的策略3 用 `patternAnyToken` 找「最后一个合法码」再取尾段。
放开后 `D-3704` 会成为 lastEnd，但动词夹取（策略1）在本次三条样本上先命中，
地点仍是「派出所南隔壁快递站」，逐条实测无变化。

## 七、地点成色校验（引擎改动，随下一版 APK 生效）

### 7.1 两条既有 bug

```
【菜鸟驿站】取件码为B-12，请到店领取      → 地点 = 店领
【菜鸟驿站】取件码16-4-9626，请到店领取   → 地点 = 店领
【妈妈驿站】取货码Z-99001，您的包裹已到店  → 地点 = 您的包裹已到店
```

两条在 v11 下都复现，与码形改动无关：

- 前者：`patternPlace` 的 lookahead 里有单独的「取」，
  `到` 后面非贪婪捕获到「店领」就满足了；而且旧代码**命中第一个匹配就直接 return**，
  就算后面真写了门店名也再没机会被看到
- 后者：`(?:已到达|到达|已到|到|至)` 命中「已到」后，非贪婪捕获一路吃到句尾 `$`

### 7.2 修法：`plausiblePlaceName()`

不猜、不补全，只做否决：

```java
private static boolean plausiblePlaceName(String s) {
    if (s == null) return false;
    String t = s.trim();
    if (t.length() < 2 || t.length() > 40) return false;
    if (containsAny(t, "包裹", "快件", "您的", "取件码", "取货码")) return false;
    if (t.startsWith("请")) return false;
    String core = t.replaceAll("[领取出拿收寄]+$", "");
    if (core.length() < 2) return false;
    return !core.matches("店|站|柜|点|门店|驿站|站点|快递|快递点|快递站|服务点");
}
```

策略1 / 策略2 从「取第一个匹配」改成「**循环找第一个合格的匹配**」，
策略3 的尾段也过同一道校验。全都不合格返回「—」。

### 8.1 发现并修掉：混排码漏抓

第一版跑下来 19 PASS / 4 FAIL，其中 3 条是真漏洞：

```
【菜鸟驿站】您的快递已存入XX菜鸟驿站，请凭取件码8A3K取件。   → 实得 []
【菜鸟驿站】取件码8A3K，请到XX小区15号楼菜鸟驿站领取        → 实得 []
【菜鸟驿站】取件码A3K8，请及时取件                          → 实得 []
```

旧 `alnumPattern = [A-Za-z]?\d{3,9}` 只覆盖「字母开头 + 3~9 位数字」，
`8A3K` 这种数字字母交替一个都不认。新增分支：

```
(?=[A-Za-z0-9]*\d[A-Za-z]\d)[A-Za-z0-9]{4,8}
```

要求出现**数字-字母-数字**的交替。第一版曾写成
「至少两个数字 + 至少一个字母 + 长度 4~8」，结果把 `iPhone15` 也抓了
（`iPhone` + `15` 满足两个数字），固化为语料后 `FAIL 165` 立刻暴露；
收紧成交替模式后 `iPhone15` / `MP3` / `A4` 全部不抓。

外层用 `(?:...)` 把两个分支包起来，是为了兼容老引擎的
`Pattern.compile("^" + alnum + "$")`——不加这层括号，`^A|B$` 会被解释成
`(^A)|(B$)`，形状校验直接失效。

### 8.2 固化进语料

新增 **145~168 共 24 条**真实样本（19 正向 / 5 反向）。语料 144 → **168 条**。
全量 14 套全过：码 168/168、地点 16/16。

## 九、为什么不能把 v13 并回 v12

版本号从 v12 走到 v13，看起来是「几句话升一版」，但把内容塞回 v12 会出事：

**① 版本比较门禁直接挡掉。** `UpdateCenter.fetchRules()` 里：

```java
if (RuleIntegrity.isNewer(cand.version, PickupExtractor.getActiveRulesVersion())) {
    applyNewRules(...);
}
return 2;  // 已是最新
```

用户手机已经拉到 v12。如果远端内容改了但版本号还是 12，
`isNewer(12, 12)` 为 false → 返回「已是最新 v12」→ **新内容永远不会应用**。

**② 同版本锚定也会拒绝。** `RuleIntegrity.verify()` 规定：拉到的版本号
等于 APK 内置版本时，摘要必须一致。同号换内容会返回 `BUNDLED_MISMATCH`（rr=4），
端侧直接拒绝更新。这道闸是为了防 CDN 劫持，不能绕。

所以 v12 一旦推出去，它的内容就**冻结**了（和 release notes 一个道理）。
要改只能往后走版本号。

从用户视角其实只有两次更新：`v11 → v12`（单段码修复，已推）和
`v12 → v13`（同一波收口）。v10 / v11 是更早的历史版本，不是这一轮产生的。

`minAppVersionCode` 保持 **405** 不变——只有规则数据变了，引擎没变，
老版本 App 依然能拉到；一旦把它往上提，4.0.5~4.1.0 的用户反而会被挡在外面。

## 十、淘宝 App 通知 + 同码合并（v13 引擎改动）

### 10.1 现象

用户提供了一条真实淘宝通知：

```
【订单物流】您购买的宝贝已送达菜鸟驿站，包裹待签收【取件码-1-9-7026】，
手机号已加密，享号码保护服务，点击查看详情>>
```

三项都不对：

| 字段 | 实得 | 期望 |
|---|---|---|
| 取件码 | `[]`（整条被否） | `1-9-7026` |
| 来源 | `订单物流`（若放行） | `淘宝通知` |
| 地点 | `—`（若放行） | `菜鸟驿站` |

### 10.2 取件码：强锚点例外

TierA 其实能抓到 `1-9-7026`，但 v9 的 `notifyOnlyPhrases` 在
`lookLikePickupSms` / `hasFeatureWords` / `extractWithRules` 三处都做了
**整条一票否决**，标题里的「订单物流」命中即返回空。

修法和 v3.1.0 处理 `negativeKeywords` 的思路一致——**强锚点优先**：
新增 `isNotifyOnly(r, body)`，命中状态通知词后，再看 `patternKeyword`
或 `patternBy` 能否给出「形状合法的码」（码簇逐段验，用 `isAnchorCluster`）。
有强锚点就不否决。

实测区分度（6 条）：

```
真通知：notifyOnly命中=true | 锚点=[1-9-7026]合法  → 放行
反例×5：notifyOnly命中=true | 锚点=无             → 照旧拦截
```

### 10.3 地点：补 placePrefixes

`patternPlace` 要求「到/至…取」夹取，原文是「已送达…待签收」没有「取」；
`patternPlaceFallback` 的前缀表只有 `已到达/到达/已到/到/在/至`，没有「送达」。
给 `placePrefixes` 加 `已送达`、`送达` 即可。这是规则数据，老引擎拉到也能生效。

### 10.4 来源：通知通道统一「xx通知」

`resolveSource` 原来先走括号品牌策略，把正文第一个【】当来源——
淘宝通知的第一个【】恰恰是标题「订单物流」，于是来源写成「订单物流」。

改成：**通知通道（`通知:<包名>`）优先按包名判定，且放在括号策略之前**。
包名→标签抽到新类 `AppLabels`（零 Android / Xposed 依赖），
`NotiHook.PKG_LABELS` 改为引用它，消除两处维护。
`AppLabels.notiSource()` 统一输出 `淘宝通知` / `菜鸟通知` / `京东通知`…，
未收录包名退到末段（`app通知`）。

抽这个类还有个实际收益：离线测试以前只能给 `NotiHook` 塞一个空 map 替身，
「通知来源」根本测不了；现在 FeatureTest 能直接验 7 条映射。

### 10.5 同码合并：后到非空覆盖，空则保留

同一个包裹常先来短信、后来 App 通知（或反过来），两条各带一部分信息：
短信可能只有来源没地点，通知可能只有地点还改写了来源。
原先只在「已有地点是 —」时补地点，**来源永不更新**，谁先到谁的内容就固定了。

改成按字段独立合并，新增 `PickupRepository.mergeField(existing, incoming)`：

| existing | incoming | 结果 | 说明 |
|---|---|---|---|
| 菜鸟驿站 | — | 菜鸟驿站 | 空保留 |
| — | 淘宝通知 | 淘宝通知 | 空被填 |
| 菜鸟驿站 | 淘宝通知 | 淘宝通知 | 后到覆盖 |

DAO 新增 `updateSourceAndPlace()` 无条件写结果值——决策全在 Java 层，
能脱离 Room 离线测试（DataTest 新增 11 条，含两个端到端顺序场景）。

## 十一、真机错题本三条误报（v13）

### 11.1 数据来源

2026-11-18 从真机 root 读取
`/data/data/io.github.okaidev.pickupcode/shared_prefs/dedup.xml` 的
`missed_sms_samples`，得到当前三条：

| # | 来源 | 原文 |
|---|---|---|
| 1 | 通知:抖音 | 客户拒收的快递没拦截住，出库后客户要拒收只能申请退货退款，没有运费险客户只能付运费>> |
| 2 | 通知:淘宝 | 您今天共有7个在途快递哦 / 点击查看详情> |
| 3 | 通知:淘宝 | 您购买的宝贝物流状态已更新 / 包裹到达新站点，点击查看>> |

没有一条是取件短信——全是电商客服话术和在途状态通知。

### 11.2 排查过程

三条的共同点：**只命中泛特征词「快递」「包裹」，没有任何码锚点**。

```
hasFeatureWords(错题本入口) = true
lookLikePickupSms            = false
notifyOnly 命中              = false
extract codes                = []
特征词 = [快递] / [快递] / [包裹]
```

`hasFeatureWords` 是错题本的入口——只要含特征词、提取为空就记。
问题在于**通知通道里「快递」「包裹」已经是泛用词**：在途、拒收、退货、
运费险全都在说快递。靠特征词判「疑似漏抓」，必然把这类通知收进来。

更关键的是：这三条正文**没有【订单物流】这种标题**，所以 v11 加的那批
状态词（`订单物流`/`商品派送通知`/`订单签收提醒`…）一个都命中不了。
它们是从统计词表里漏出去的另一种写法，不是同一批样本的变体。

### 11.3 修法

补 4 条精准短语进 `notifyOnlyPhrases`：

```
在途快递  物流状态已更新  客户拒收  退货退款
```

刻意用「客户拒收」而不是单用「拒收」——后者太宽，
「您的包裹被拒收请取回」这类含码的真短信存在误杀风险。
即便如此仍有第二道保险：`isNotifyOnly` 的强锚点例外会放行带合法码的短信。

### 11.4 验证

| 样本 | hasFeatureWords | 结果 |
|---|---|---|
| 三条真机错题 | false | 不再进错题本 ✓ |
| `【菜鸟驿站】您有包裹在途，取件码1-9-7026，请到店领取` | true | 出码 ✓ |
| `【菜鸟驿站】退货件已到，取件码5-1-6046，请及时取件` | true | 出码 ✓ |
| `【菜鸟驿站】客户拒收件已退回本店，取件码6-8-5021，请领取` | true | 出码 ✓ |

语料 **173 → 179 条**（174~176 三条真机反例 + 177~179 三条带否决词的真取件正例），
端侧冒烟同步补 3 条反例。全量 14 套全过：码 **179/179**、地点 **16/16**。

### 11.4 这类问题的通用排查路径

以后再遇到「错题本里混进非快递内容」，按这个顺序查，不要直接往
`negativeKeywords` 里加词（那只作用于 TierD 弱兜底，管不到错题本入口）：

1. 从真机 `dedup.xml` 的 `missed_sms_samples` 导出原文——不要靠截图手抄
2. 打印 `hasFeatureWords` / `lookLikePickupSms` / `notifyOnly` 命中 / 命中的特征词
3. 若只有泛词无锚点 → 补 `notifyOnlyPhrases`，用词要**精准且带语境**
4. 补完必须验「带码短信顶着同样的话术仍能出码」——强锚点例外是第二道保险
5. 三条反例 + 三条边界正例一起固化进语料和端侧冒烟
