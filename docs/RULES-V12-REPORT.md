## 一、现象

三条真机原文，同一个菜鸟驿站模板：

| # | 短信原文 | v11 提取 | 正确结果 |
|---|---|---|---|
| 1 | 【菜鸟驿站】取件码D-3704的韵达81913包裹到派出所南隔壁快递站，请19:00前取 | `3704`、`81913` | `D-3704` |
| 2 | 【菜鸟驿站】取件码D-3770的韵达39116包裹到派出所南隔壁快递站，请19:00前取 | `3770`、`39116` | `D-3770` |
| 3 | 【菜鸟驿站】取件码C-2605的韵达30453包裹到派出所南隔壁快递站，请19:00前取 | `2605`、`30453` | `C-2605` |

两个错码的性质并不相同：

- `3704` 是**真码自己的尾段**——`D-3704` 被横杠切开后的后半截
- `81913` 是**韵达运单尾号**，与取件码毫无关系

来源（菜鸟驿站）与地点（派出所南隔壁快递站）在 v11 下都是对的，问题只在码。

## 二、归因：锚点层抓对了，是形状校验把它扔了

把引擎逐层打开看（`test/RuleLab` 之外的临时探针）：

```
TierA hit: [D-3704] @9          ← 锚点层其实抓对了整串
validCode("D-3704") = false     ← 形状校验判非法，直接丢弃
CODES = [3704, 81913]           ← 结果集为空 → 退化到 TierD 弱兜底
```

`dashPattern`（v11）：

```
(?:[A-Za-z]{1,2}-\d{1,6}|[A-Za-z]{0,2}\d{1,6})(?:-(?:…)){1,3}   ← 至少两段
```

`D-3704` 拆开是两个字段：`D` 和 `3704`。第一段的形状表只有「字母-数字」和
「数字」两种，**没有纯字母段**；唯一能整串吃下它的 `[A-Za-z]{1,2}-\d{1,6}`
后面又强制要求 `(?:-段){1,3}`（至少再来一段）。于是整串被判非法。

结果集为空 → 落到 TierD：

- `anyToken` 的 lookbehind 是 `(?<![A-Za-z0-9])`（v6.1 为了让「取件码-6-4-3009」
  能抓到横杠后面的码而放宽），横杠不算字母数字，于是从 `-` 后重新起扫
- `3704` 和 `81913` 都是纯数字，`alnumPattern` 全部放行
- 两个 token 在 24 字窗口里都能同时够到「包裹」和「取件」，
  评分各得 4 分（阈值就是 4），双双通过

一句话：**正确的答案在第一步就被扔掉了，兜底层只能用碎片拼一个看起来像的东西。**

## 三、修法（三处，全在规则数据里）

### 3.1 `dashPattern`：允许单段「字母-数字」

```
(?:[A-Za-z]{1,2}-\d{1,6})(?:-(?:…)){0,3}          ← 新增：字母-数字开头，尾段 0~3
| (?:[A-Za-z]{1,2}-\d{1,6}|[A-Za-z]{0,2}\d{1,6})(?:-(?:…)){1,3}
| (?:[A-Za-z]{1,2}-\d{1,6}|[A-Za-z]{0,2}\d{1,6})(?:-[A-Za-z]{1,2})(?:-(?:…)){1,2}
```

关键是**分开写**而不是把原分支的 `{1,3}` 改成 `{0,3}`：

- 「字母-数字」开头 → 允许 0 尾段（`D-3704`、`C-2605`、`M-2`）
- 纯数字开头 → 仍要求至少 1 尾段（`16-4-9626`、`9-9999`）

如果把 `{1,3}` 统一改成 `{0,3}`，`[A-Za-z]{0,2}\d{1,6}` 会连 0 尾段一起合法化，
**裸数字（`6`、`189`、`1064`）立刻变成合法码形**——v4 时代专门修过的坑会重新裂开。

### 3.2 `excludeHeadWords`：补 18 个承运商名

```
韵达 中通 圆通 申通 顺丰 邮政 EMS 极兔 德邦 京东 百世 天天 优速 宅急送 丰网 速尔 全峰 国通
```

语义：品牌名后面紧跟的纯数字是运单尾号（`韵达81913`），不是取件码。

为什么不会误杀正常取件短信：锚点层抓到的码，前文是「取件码／取货码／凭／出示」，
碰不到品牌名；只有兜底层才会遇到「品牌名 + 数字」这种紧邻关系。

### 3.3 `excludeTailPhrases`：补 7 个物流状态词

```
已发货 已发出 已寄出 已揽收 已签收 派送中 运输中
```

对抗测试里发现的独立误抓：`【京东】您的快递JD-889900已发货，请及时领取`
在放开单段码形后会被抓成 `JD-889900`（v11 抓的是 `889900`，同样错）。
码后紧跟「已发货」这类状态词，说明它是运单号而不是取件码。

刻意**没有**加入「已到站」「已到达」——这两个词在真实取件短信里紧跟在取件码后面
（「取件码D-3704已到站，请及时领取」），加进去会大面积误杀。

## 四、为什么不改引擎

这次连一行 Java 逻辑都没动，只改了 `rules/rules.json` + 冒烟用例表。原因是：

1. **热更新能覆盖到已经装机的用户**。引擎改动必须发版，而规则改动走 `UpdateCenter`
   的双镜像拉取，3 天内自动生效，用户什么都不用做。
2. **老引擎能正确解释新规则**。`dashPattern` / `excludeHeadWords` / `excludeTailPhrases`
   都是 4.0.5 起就存在的字段（`minAppVersionCode = 405`），语义没有扩展，
   只是词表和形状放宽。
3. **已经有实测证据**：用 v4.1.0 编译产物里那份**旧冒烟用例**（`SMOKE_TEST_CASES`）
   跑 v12 规则，`runSmokeTest` 返回 `true`。也就是说老 App 拉到新规则不会被
   端侧安全闸拒绝。

所以 `minAppVersionCode` 保持 **405** 不变。

## 五、影响面

`dashPattern` 是全局码形，同时喂给四处：

| 使用点 | 影响 |
|---|---|
| `validCode()` | 单段字母码从「非法」变「合法」——本次要的修复 |
| `patternAnyToken`（TierD / 地点策略3） | token 边界变正确：`D-3704` 整串被吃下，不会再有 `3704` 碎片 |
| `patternBy`（TierB「凭/出示」） | `凭A-1234到…取件` 能命中 |
| `patternCodeToTake`（TierC） | 「码…到…取」夹取型覆盖单段码 |

`extractPlace` 的策略3 用 `patternAnyToken` 找「最后一个合法码」再取尾段。
放开后 `D-3704` 会成为 lastEnd，但动词夹取（策略1）在本次三条样本上先命中，
地点仍是「派出所南隔壁快递站」，逐条实测无变化。

## 七、本轮未修（已确认是既有问题，不是 v12 引入）

### 7.1 「请到店领取」被当成地点

```
【菜鸟驿站】取件码为B-12，请到店领取     → 地点 = 店领
【菜鸟驿站】取件码16-4-9626，请到店领取  → 地点 = 店领
```

`patternPlace`（动词夹取）的 lookahead 里有单独的「取」，
`到` 后面非贪婪捕获到「店领」就满足了。v11 下同样如此，与本次改动无关。

### 7.2 「您的包裹已到店」被整句当成地点

```
【妈妈驿站】取货码Z-99001，您的包裹已到店  → 地点 = 您的包裹已到店
```

同样在 v11 下复现。`(?:已到达|到达|已到|到|至)` 命中「已到」后，
非贪婪捕获一路吃到句尾 `$`。

### 7.3 5.0 规划区的规则副本落后

`5.0-规划资料库/08-5.0工程工作区/pickup5/rules/rules.json` 仍是 `version: 10`。
不在发布链上，本轮未动；5.0 合并时需重新以 `rules/rules.json` 为准同步。
