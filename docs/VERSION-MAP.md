# 版本映射：3.1.0 → 3.2 … 3.9 → 4.0.0

> 目的：把本地从 4.0 改到 4.8 的“内部迭代编号”收口成一条正常的版本阶梯。
> 原则：**不重写 Git 历史**，只增加内部标签与映射文档；对外只发布 `v4.0.0`。

## 一、结论

- 线上最后一个公开稳定版：**3.1.0**。
- 当前本地 v4.8 不是公开版本，整体视为 **3.6.0 内部里程碑**。
- 4.0 发布前，内部按 **3.2.0 → 3.9.0** 推进；**4.0.0 是唯一对外版本**。
- 公开仓库不出现 4.1–4.8 的 Release/Tag；现有提交说明里的 v4.x 作为历史代号保留，由本文档解释。
- 内部标签统一用 `internal/3.x.0`，只在本机保留；公开标签只有 `v3.1.0` 与最终的 `v4.0.0`。

## 三、版本号与构建号规则

| 版本 | versionName | versionCode | 界面显示 | 用途 |
|---|---|---|---|---|
| 3.1.0 | `3.1.0` | 310 | V310 | 线上稳定版 |
| 3.2.0–3.6.0 | `3.x.0` | 320–360 | V3xx | 历史里程碑 / 本地回溯 |
| 3.7.0 | `3.7.0` | 370 | V370 | 安全与分层 |
| 3.8.x | `3.8.x` | 380–381 | V38x | 本地库与小组件 |
| 3.9.x | `3.9.x` | 390–394 | V39x | 双模式 UI、规则集 v7 |
| 4.0.0 | `4.0.0` | 400 | V400 | 对外毕业版 |

> **界面显示规则（2026-10-30 起）**：应用内统一显示 **V + versionCode**（纯数字，如 V394），
> 不再出现 `-internal` 之类后缀——内部发布节奏用 git tag 与本文档表达，用户侧不需要知道。
> 同时首页头部只放这一行，不再拼接说明文字，避免折行。

实现要求：

- 新增 `version.properties`，Gradle 只从这里读 `versionName/versionCode`。
- `app/AndroidManifest.xml` 删除硬编码的 `versionCode/versionName`，避免再出现 310/3.1.0 与 400/4.0.0 并存。
- `BuildConfig` / 界面版本号统一读取 Gradle 注入值。
- CI 增加 `checkVersion`：tag 必须是 `v4.0.0`，APK 的 versionName/Code 必须与 tag 一致。

## 四、Changelog 收口规则

最终 `CHANGELOG.md` 只保留：

1. `[4.0.0]`：面向用户的完整变更（UI、双模式、本地库、小组件、安全、兼容性）。
2. `[3.1.0]`：上一个公开版。
3. 附录 `Internal iterations 3.2–3.9`：一张映射表，指向本文档，不展开成 8 个公开版本。

现有 `[3.1.1]` 未公开发布，折叠进 4.0.0 的“修复”段；不再单独占版本。

## 五、为什么不重写 Git 历史

- 20 个提交里有大量真机排查过程（ColorOS 类名、弹窗根因、包可见性、通知字段），改写/压缩容易丢证据。
- 代码与提交已经稳定，重写历史的风险高于收益。
- 公开版本号由 tag 与 Changelog 决定，不由提交标题决定；映射文档足以消除“3.1 直接跳到 4.8”的观感。
- 如果最终确实需要“干净公开历史”，可在发布前另建 `release/4.0` 分支做一次 squash，但这是可选项，不作为默认方案。

## 六、发布时的版本动作

1. 在 `release/4.0` 分支把 `version.properties` 改为 `4.0.0 / 400`。
2. 更新 `CHANGELOG.md`，只保留 4.0.0 与 3.1.0，追加内部迭代附录。
3. 更新 README、LSPosed 模块描述、酷安文案、截图。
4. 构建签名 APK，校验 `versionCode=400`、`versionName=4.0.0`、证书 `CN=PickupCodeGrabber`。
5. 打 tag `v4.0.0`；**经用户确认后**再 push / Release / 同步 LSPosed 镜像。
