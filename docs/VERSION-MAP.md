# 版本号规范（4.0.2 起，全项目统一）

> **一句话**：全项目只维护**一个**点分版本号，界面、Git 标签、文档、规则兼容性
> 全部用它。`versionCode` 由它推导，不单独维护、不参与展示。

---

## 一、格式与语义

```
V<大版本>.<小版本>.<修复版本>
```

| 段位 | 含义 | 什么时候 +1 | 例 |
|---|---|---|---|
| 第一段 | **大版本** | 不兼容的架构/功能变更 | 3 → 4 |
| 第二段 | **小版本** | 新增功能 | 4.0.0 → 4.1.0 |
| 第三段 | **修复版本** | 修 bug | 4.1.0 → 4.1.1 |

**例子**：现在属于第四个大版本，所以是 `4.0.0`；加小功能可能是 `4.1.0` 或 `4.2.0`；
修 bug 则是 `4.2.1` 或 `4.2.2`。

---

## 二、唯一事实源

`version.properties`（仓库根目录）——**只写这一行**：

```properties
VERSION_NAME=4.0.2
```

`versionCode` 由构建脚本按固定公式推导：

```
versionCode = 大版本 × 10000 + 小版本 × 100 + 修复版本
```

| 版本号 | versionCode | 界面显示 |
|---|---|---|
| 4.0.2 | 40002 | `V4.0.2` |
| 4.1.0 | 40100 | `V4.1.0` |
| 4.1.1 | 40101 | `V4.1.1` |
| 5.0.0 | 50000 | `V5.0.0` |

**为什么推导而不单独维护**：原先 `VERSION_NAME` 与 `VERSION_CODE` 是两个独立数字，
改一处忘另一处就会出现「界面显示 4.0.0、规则兼容性却按 293 判」这类说不清的问题。
现在只有一个数需要人改，其余全部派生，不可能对不上。

---

## 三、格式守卫（构建期强制）

`app/build.gradle` 的 `checkVersionConsistency` 任务会校验：

- `VERSION_NAME` 必须匹配 `^\d+\.\d+\.\d+$`——**带 `-internal` / `-rc2` 后缀直接构建失败**；
- `AndroidManifest.xml` 里不得硬编码 `versionCode` / `versionName`；
- `versionCode` 必须 ≥ `30100`（已发布的 3.1.0 在新方案下的构建号）。

`AppVersion` 里也**不再做后缀容错**——那是历史包袱：
早期版本名带后缀导致版本比较抛异常被吞掉，「自动检查更新」永远认为已是最新。

---

## 四、涉及版本号的各处，统一规则

| 位置 | 用什么 | 备注 |
|---|---|---|
| 界面头部副标题 | `V4.0.2` | `AppVersion.label()` |
| 头部署名 | `design by 欧锴` | 版本号后面，跟版本号不同字号/颜色 |
| 「项目版本信息」弹窗 | `V4.0.2` + 构建号 | 构建号只在这里作为补充信息出现 |
| 「关于模块」弹窗 | `V4.0.2` | |
| 诊断报告（文本 / JSON） | `V4.0.2` | JSON 里 `version` / `versionLabel` / `versionCode` 分开 |
| Git 标签 | `v4.0.2` | 与版本号完全一致，不加 `-rc1` 之类 |
| CHANGELOG 标题 | `## 4.0.2` | 与版本号一致 |
| 规则集 `minAppVersionCode` | 同套数字 | 例如「需要 4.0.0 以上」写 `40000` |

**唯一的例外**：`versionCode` 会出现在「项目版本信息」弹窗与 JSON 诊断报告里，
因为排查问题时需要它和 `minAppVersionCode` 这类闸门对照。它不参与任何界面展示。

---

## 五、Git 标签约定

- 标签名 = `v` + 点分版本号，例如 `v4.0.2`。
- **不加任何后缀**（`-rc1` / `-internal` / `-v2` 一律不用）。
- 旧标签不重写、不删除（Git 历史不可变），但从 4.0.2 起不再产生带后缀的标签。

---

## 六、代码里的唯一出口

`AppVersion`（`app/src/io/github/okaidev/pickupcode/AppVersion.java`）：

| 方法 | 用途 |
|---|---|
| `dotted(ctx)` | 点分版本号，如 `4.0.2` |
| `code(ctx)` | 构建号，如 `40002`（只给升级判定与兼容性闸门） |
| `label(ctx)` | 界面标签，如 `V4.0.2` |
| `compare(a, b)` / `isNewer(a, b)` | 版本比较（与解析同源，不再各写一份） |

**不要在别处直接读 `PackageInfo.versionName` 或 `versionCode`**——
那正是「同一份内容散在多处」的源头。

---

## 附：历史版本号对照（仅供追溯，不再作为现行规则）

4.0.2 之前，项目曾用过两套并存的数字：界面显示构建号（V400）、
而更新检查与规则兼容性用另一套数字。加上 3.2–3.9 的内部迭代阶梯，
一共出现了三种版本表述方式。

从 4.0.2 起全部收口为上面这一套。旧标签（`internal/3.x.0`、`v4.0.0-rc1` 等）
作为 Git 历史保留，但**不代表现行版本规则**。
