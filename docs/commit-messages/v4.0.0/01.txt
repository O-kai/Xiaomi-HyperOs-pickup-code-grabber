fix(engine): 规则集 v6 —— 修复三条漏抓短信，统一短信/通知门禁

起因是三条真实短信识别不出来（驿小哥、包裹待签收、拼多多通知），
逐层排查后发现是三处独立的规则缺陷叠加，外加一处通道门禁不一致。

## 一、驿小哥「凭4-3-5120免费取」识别不出

短信原文：
  【驿小哥】您的快递圆通，已到江南绿城西门北50米顺丰速运驿收发，
  凭4-3-5120免费取，如有疑问可到店咨询，谢谢。

两处叠加：
- TierB（凭/出示 锚点）的后瞻词表里没有「免」字。原文取件码后面紧跟的是
  「免费取」而不是「到…取」，后瞻匹配失败，TierB 整层不命中。
- TierD（严格评分兜底）只得了 3 分，阈值是 4。原因是特征词表里只有「驿站」，
  而原文写的是「驿收发」——「驿收发」是顺丰旗下的驿站品牌，不是「驿站」的子串，
  特征词一个都没命中，评分差 1 分卡在阈值下。

修复：
- byLookaheadWords 补入 免 / 可 / 即 / 立 / 自 / 请 / 务
- featureWords 补入 驿收发 / 驿小哥 / 快宝 / 小兵驿站 / 邻里驿站

结果：extract → [4-3-5120]

## 二、「包裹待签收【取件码-6-4-3009】」识别不出

这条是三处缺陷叠加，每一处单独都能让它失败：

1) 锚点到取件码之间的横线被吃进了捕获组
   原文「取件码-6-4-3009」的「-」被 pKw 的分隔符类吃掉后，
   捕获到的是「-6-4-3009」，不是合法取件码形状。
   修复：分隔符字符类补入 \-—–（半角横线 / 全角破折号 / en dash）。

2) patternAnyToken 的前向断言把取件码排除了
   原断言 (?<![A-Za-z0-9-]) 要求取件码前不能是字母数字**或横线**，
   而这条短信里取件码前面正好是「码-」，于是 lookLikePickupSms 返回 false，
   兜底通道直接不进入。
   修复：放宽为 (?<![A-Za-z0-9])，只排除字母数字，不再排除横线。

3) 地点被误解析成「】，手机号已加密，享号码保护服务，点击查看详情>>」
   原因是「服务」在 place 后缀词表里，而「号码保护服务」恰好以它结尾。
   修复：
   - 地点解析前先剥离右括号与标点（】》」）)\] 等）
   - looksLikePlace 增加噪音否决词：号码保护 / 已加密 / 加密 / 点击查看 /
     详情 / 退订 / 回复 / 客服 / 咨询 / 如有疑问 / 谢谢

结果：extract → [6-4-3009]，地点为空（正确）

## 三、通知通道与短信通道门禁不一致

NotiHook 在解析前有一道 hasFeatureWords 前置门禁，不命中就直接 return。
后果是「有取件码但没有特征词」的通知被静默丢弃，连漏抓错题本都进不去，
用户完全看不到痕迹。

而短信通道（SystemDirectWriter）用的是 lookLikePickupSms。
两条通道对同一段文本的判定标准不同，是隐患。

按统一门禁的方案改为两边都用 hasFeatureWords：
- SystemDirectWriter 的 lookLikePickupSms 改为 hasFeatureWords
- NotiHook 移除前置 return，改为无条件尝试提取；
  只有「有特征词但没提取到码」时才记入漏抓错题本
