有用户报了一条短信：**「您有2个包裹在xx待取，请凭1-3-1257, 2-4-0274等取件码」**——
App 只认出了第一个。

这一版就是修这个：**一条短信里有几个取件码，就出几条待取件**。

### 为什么之前只出一个

识别靠「锚点 + 码」。「取件码 A、B、C」这种写法，锚点在前面，本来就能把一整串拆开；
但「**凭** A, B **等取件码**」把锚点放在最前面、末尾用「等」收口，这条路径的正则
只捕获**一个**码——后面那些根本没进候选列表。

偶尔也能出全，那是最后的兜底逻辑顺手把散落的码捞了回来，不稳定，取决于句式。

### 现在怎么处理

- 锚点后面改成抓**整个码簇**（`A, B, C`），再逐个拆开
- 末尾允许「等 / 均 / 都」收口——「…2-4-0274**等**取件码」这种断句现在是对的
- 每个码独立成一条：系统待办一条、App 内「待取件」一条、桌面组件一行

实测覆盖：

| 写法 | 结果 |
|---|---|
| `请凭1-3-1257, 2-4-0274等取件码` | 2 条 |
| `取件码1-1-1111、2-2-2222、3-3-3333` | 3 条 |
| `取件码：5-1-8801，5-1-8802，5-1-8803，5-1-8804` | 4 条 |
| `请凭1-3-1257、2-4-0274、3-5-6789等取件码到店取件` | 3 条 |

同时确认没有被带偏：验证码短信、客服电话这类仍然不提取。

### 规则集 v10

- 版本号 **v10**
- `minAppVersionCode` 提到 **405**：拆簇逻辑写在代码里，
  老版本即使下载了 v10 规则也还是只认第一个码——所以这一版规则不推给老版本，
  它们保持原来的行为，不会变得更糟
- **要拿到这个修复，必须升级到 4.0.5**（不是只更新规则）

### ⚠️ 升级注意

1. 装完**重启手机**：抓取逻辑在系统进程里，LSPosed 只在进程启动时注入；
2. 这条短信如果已经收过了，不会重新解析——去「一键链路测试」里贴一遍原文即可验证；
3. 之前只记下一个码的那几条历史记录，需要手动补一条（模块不会回头重扫短信）。
