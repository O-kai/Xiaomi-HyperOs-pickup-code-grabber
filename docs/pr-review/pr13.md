# PR #13 评论（可直接粘贴到 GitHub）

> 标题：fix(coloros): 模块被划掉/冻结后，由 system_server 放行 Provider 唤醒（KernelSU 可用）
> 结论：**已移植到 `release/4.0`**（v4.0.2）。

---

感谢 @ByteJuno。这个 PR 的价值不只是「修一个 ColorOS 的坑」——
它指出了一件我们之前没想清楚的事：

> 「冻结免疫直写」需要给短信进程授权 root，而短信进程是 UID 1001，
> **KernelSU 内核直接禁止 UID < 2000 取 su**，所以 KSU 用户根本开不了这个兜底。

这条对 4.0 尤其重要：4.0 把跨进程入口收成了 Provider 单入口
（删掉了导出的广播 receiver），一旦 Provider 唤不醒，**整条链路就断了**，
没有广播可以退。所以这个放行点是刚需，不是优化。

## 一、移植情况

- 新增 `app/src/io/github/okaidev/pickupcode/ColorOsProviderWake.java`，
  逻辑与你的实现一致（四道 gate：`interceptStartProvider` /
  `hookHansProviderIfNeeded` / `hookbeforeInactiveProviderGet` / `hookPreloadProviderBlock`，
  只放行「目标是本模块 Provider + 调用方 system/phone」）。
- `XposedEntry` 在 system_server 分支里调用 `ColorOsProviderWake.install()`。
- `NotiRelay` 的「Provider 优先」在 4.0 里本来就是——4.0 已经完全不用导出广播了，
  所以这部分没有改动；但我采纳了你「不要卡在 NMS 入队线程」的思路，
  把 Provider 调用整体移到后台线程。

## 二、我额外加的两处防御

1. **返回类型检查**：`hookAllMethods` 是按方法名挂的，
   如果某个 ROM 把同名方法改成 `void`，`setResult(Boolean.FALSE)` 会破坏系统调用。
   现在先判断 `getReturnType()` 是 `boolean`/`Boolean` 才动，否则完全不碰。
2. **日志分级**：非 ColorOS 上打印的是 `WAKE skip: ... not found (non-ColorOS)`，
   明确写成「正常跳过」而不是错误，避免用户看日志以为出问题。

## 三、HyperOS 上的行为（重点）

找不到 `com.android.server.am.ContentProviderHelperExtImpl` 这个类，
`findClassIfExists` 返回 null，`install()` 直接 return。

- 不注册任何 hook；
- 不改变任何系统行为；
- 只留一行 `WAKE skip` 日志。

也就是说：**小米设备上这个类完全不参与**，风险为零。
这一点我是按「宁可什么都不做，也不能误伤」的原则处理的。

## 四、还需要你在 ColorOS 上确认

重启后预期日志：

```
PICKUPDEBUG: WAKE OK: 4 provider gate(s) hooked
PICKUPDEBUG: WAKE allowed: gate=interceptStartProvider caller=com.android.providers.telephony uid=1001
```

验证步骤建议：
1. 把模块从最近任务划掉；
2. 发一条取件短信 / 触发一条取件通知；
3. 看取件码是否还能写进去，以及日志里有没有 `WAKE allowed`。

如果 `WAKE OK: 0 provider gate(s) hooked`，说明这个 ROM 版本的门禁方法名变了，
把 ROM 版本号和 `dumpsys` 里那个类的信息发我，我再补候选方法名。

代码随 v4.0.2 发布，CHANGELOG 会署名。谢谢！
