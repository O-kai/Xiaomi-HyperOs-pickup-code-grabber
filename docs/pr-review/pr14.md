# PR #14 评论（可直接粘贴到 GitHub）

> 标题：fix(noti): 通知通道在 ColorOS 17 / Android 16 上收不到取件码的修复
> 结论：**采纳并移植到 `release/4.0`**（v4.0.2），8 项直接落地、3 项在 4.0 里已经是更严格的实现。

---

感谢 @ByteJuno，这份排查质量很高——尤其是「`args.length < 10` 会让整条通道静默失效」
和「全局 `lastWriteDiag` 在并发下会误报」这两条，我们 4.0 分支上也确实存在，已按你的思路修掉。

需要说明一点：这个 PR 的 base 是 `main`（= 3.1.0），而维护分支 `release/4.0`
已经比它领先 62 个提交（4.0 重写了 UI、把跨进程入口收成 Provider 单入口等）。
所以我没有直接 cherry-pick，而是**逐条对照移植**，并针对 4.0 的现状做了适配。

## 一、已采纳（4 项）

| 改动 | 落地位置 | 说明 |
|---|---|---|
| 通知入队参数校验放宽 | `NotiHook.handleEnqueue` | 改成 `args[0] instanceof String` + `findNotification()` 兜底，见下方安全性说明 |
| 30 秒事件节流 | 新增 `NotiEventWindow` | 完全按你的实现，另加了单测（`test/NotiEventWindowTest.java`，8 项） |
| 只取公开文本字段 + 长度上限 | 新增 `NotificationText` | 在你的字段集基础上保留了 MessagingStyle 的反射兜底（部分 ROM 的 `android.messages` 为空） |
| 配置 30 秒热重载 | `NotiHook.refreshConfig()` | 按 `app_state.json` 的 mtime 判断，改完设置最多 30 秒生效，不用重启 |
| 内置白名单补回 | `NotiHook` 重建白名单处 | 这条是个真 bug：旧代码 `clear()` 后只填快照，一旦快照为空/来自旧版本，**内置白名单会整份丢失** |
| 抖音白名单 | `BUILTIN_PKGS` / `PKG_LABELS` | 已加 `com.ss.android.ugc.aweme` |
| 结构化回执 | `TodoWriter.HandleResult` + `TodoProvider.call` | Provider 返回 `status / code_count / written_count / dedup_count / failed_count`，不再看全局状态 |
| 配置文件可读性 | `ProcessSync.readableConfigCommand` | `chmod 755` + `chcon system_data_file`，只处理配置文件，不碰 sqlite3 与依赖库 |

## 二、4.0 里已经是更严格实现，因此没有照搬（3 项）

1. **`SmsEventReceiver` 的 `miss` 类型修复** —— 4.0 已经把广播入口整个删掉了
   （`SmsEventReceiver` 不存在），`NotiRelay` 只走 `ContentResolver.call`，
   且 `miss` 一直是 `putBoolean`。这个 bug 在 4.0 不存在。
2. **`NotiRelay` 改成 Provider 优先** —— 4.0 本来就是 Provider 单入口
   （原因：导出的广播任何 App 都能伪造取件短信）。但我**采纳了你的异步化建议**：
   原来是在 `enqueueNotificationInternal` 的钩子里同步调用，冷启动模块进程会把
   system_server 的通知入队线程卡住几百毫秒，现在放到 `pickup-noti-relay` 线程。
3. **设置页开关「永远是关」** —— 4.0 的现象与你描述一致（App 沙箱进不去
   `/data/local/tmp`，`f.exists()` 恒为 false）。采纳结论，但实现方式调整了：
   以本地偏好为显示来源，**只在已有常驻 root 通道时**才回读文件校对。
   原因是 4.0.2 刚把「打开 App 就弹 Magisk 授权」清干净，
   不能在渲染设置页时再唤一次 `su`。

## 三、HyperOS 侧验证（我这边能做的）

真机 REDMI K90 Pro Max / HyperOS 4.0 / Android 17：

```
# 以系统身份调 Provider（模拟短信/通知进程）
content call --uri content://io.github.okaidev.pickupcode.provider --method onSms ...
Result: Bundle[{status=written, code_count=1, written_count=1, dedup_count=0,
                failed_count=0, result=[8-1-2345], rc=0}]

# 同一条再来一次
Result: Bundle[{status=deduplicated, code_count=1, written_count=0, dedup_count=1}]

# 换一条新码
Result: Bundle[{status=written, result=[6-7-8899]}]

# 日志
RootShell ready via su
root shell exec: exit=0
TODO OK: code=8-1-2345
PROVIDER-CALL: status=written codes=1 written=1 dedup=0 failed=0
```

参数校验放宽的安全性：新写法后面紧跟 `findNotification(args)`，
找不到 `Notification` 就直接 return——对真通知两种写法都通过，
对非通知调用由 `instanceof Notification` 拦住，不会误处理。

补充一条与你相关的实测（v4.0.2 第十轮）：

`chcon` 在 HyperOS 4.0 / Android 17 上**可用**（`rc=0`，标签确实变成
`u:object_r:system_data_file:s0`），三个配置文件（`app_state.json` /
`enable_noti_hook` / `user_rules.json`）现在会在**每次写入时自动 chmod+chcon**，
并在首次完整体检时补一次历史遗留文件。同时把「读不到」和「读到了」分开记日志：

```
config reloaded (mtime=..., rules=8123B, pkgs=14)      ← 真的读到并生效
config NOT readable -> load() 返回 null（SELinux 标签/目录权限？）  ← 需要修
```

原先只要 mtime 变了就打「reloaded」，`load()` 返回 null 也照打——日志看着正常、
实际用的还是内置规则，排查时会被这条假日志带偏。这个坑也顺手补了。

另外，体检里新增了一项「配置快照」，直接显示三个文件的 SELinux 标签，
以后再遇到类似问题不用靠猜。

回归：14 套、493 项断言全绿（新增 `NotiEventWindowTest` 8 项）。

## 四、还需要你在 ColorOS 上确认

`NotiHook` 跑在 system_server，**必须重启手机**才会加载新代码（LSPosed 在进程启动时注入）。
重启后麻烦确认两件事：

1. `XposedBridge` 日志里应出现 `config reloaded (mtime=...)`（说明配置热重载生效）；
2. 任意一条菜鸟/京东/抖音取件通知能被写入。

如果 `chcon` 在你的 ROM 上不可用（命令失败是静默的），
会退化成「读不到快照 → 用编译内置规则」，功能不会坏，但热重载不生效——
到时候把 `logcat | grep PICKUPDEBUG` 的结果贴给我，我再调。

代码会随 v4.0.2 一起发布（`release/4.0` 分支），届时会在 CHANGELOG 里署名。
再次感谢这份细致的排查 🙏
